Building a Custom MCP Server: Giving an LLM Safe Hands

📅 July 2026 ⏱️ 8 min read 🏷️ MCP · Node.js · LLMs

Large language models are excellent at reasoning and terrible at knowing things they were never told. Every production chatbot eventually hits the same wall: the model needs live data — a user's account state, a document, a database row — and pasting everything into the prompt is slow, expensive, and insecure. The Model Context Protocol (MCP) is the emerging standard that solves this properly: instead of stuffing context in, you hand the model a set of tools it can call on demand, through a server you control.

At Ionixx I built a custom MCP server in Node.js to power an AI chatbot on Anthropic's models. This article walks through the architecture, the consent layer that made it production-safe, and the streaming decision that cut our first-token latency by 45%.

What MCP Actually Is

Strip away the buzz and MCP is a small JSON-RPC contract between two parties:

  • An MCP client — usually the app hosting the LLM conversation — that discovers and invokes tools.
  • An MCP server — your process — that advertises tools, executes them, and returns structured results.

The whole discovery handshake is two methods. The client asks what exists:

// client → server
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {} }

// server → client
{ "jsonrpc": "2.0", "id": 1, "result": { "tools": [
  { "name": "get_account_summary",
    "description": "Returns the signed-in user's balances and positions",
    "inputSchema": { "type": "object", "properties": {
      "currency": { "type": "string", "enum": ["USD", "INR"] } } } }
] } }

…and later asks to run one:

{ "jsonrpc": "2.0", "id": 2, "method": "tools/call",
  "params": { "name": "get_account_summary",
              "arguments": { "currency": "INR" } } }

That's the core of it. The power isn't in the protocol's complexity — it's in the separation of concerns. The model never touches your database, your filesystem, or your API keys. It only ever sees tool names, descriptions, and results you chose to return.

The Architecture

Web UI  ⇄  SSE stream  ⇄  Node.js MCP server (Express)
                               │  tool registry + consent gate
                               ├── Anthropic API (Claude)
                               ├── Postgres (user data)
                               └── Web search / code exec sandbox

Three design rules shaped everything:

  • The server owns the tool registry. Tools are declared in one place with a JSON Schema for their inputs. Schema validation happens server-side before execution — never trust that the model produced well-formed arguments, because roughly 1 call in 50 it won't.
  • Every tool is a pure function of (arguments, session). The session — who is logged in, what they've consented to — comes from the authenticated transport, never from the model's arguments. If the model asks for another user's data, there is structurally no way to express that request.
  • Results are structured, not prose. Tools return compact JSON, and the model does the phrasing. This keeps token usage predictable and lets the same tools serve multiple prompts.

The Consent Gate

The part I'd call genuinely novel in our build: consent-based context. Financial data was involved, so "the model can silently read your accounts" was never acceptable. Every tool in the registry carries a sensitivity level, and the gate sits between tools/call and execution:

const TOOL_POLICY = {
  get_market_news:      { consent: "none"     },  // public data
  get_account_summary:  { consent: "session"  },  // ask once per session
  execute_transfer_sim: { consent: "explicit" }   // ask every single time
};

async function callTool(name, args, session) {
  const policy = TOOL_POLICY[name];
  if (policy.consent !== "none" && !session.hasConsent(name, policy.consent)) {
    // Pause the tool call and surface a consent prompt in the UI.
    // The model receives a structured "consent_pending" result —
    // it knows to tell the user why it's waiting.
    return { status: "consent_pending", tool: name };
  }
  validate(TOOL_SCHEMAS[name], args);   // throws on bad input
  return await TOOL_HANDLERS[name](args, session);
}

Two details made this work in practice. First, the consent prompt is rendered by the application UI, not written by the model — users approve a fixed, auditable sentence, not whatever the LLM decided to say. Second, the model receives the consent_pending status as a first-class result, so it responds naturally ("I've requested access to your account summary — approve it and I'll continue") instead of hallucinating an answer it never fetched.

Streaming: The 45% Win

Our first version buffered the whole model response server-side, then returned it in one JSON payload. Median time-to-first-word: about 4 seconds. Users read that as "broken."

The fix was Server-Sent Events end-to-end: Anthropic's streaming API already emits tokens as they're generated, so the server's job is just to relay deltas the moment they arrive:

app.get("/chat/stream", async (req, res) => {
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");

  const stream = await anthropic.messages.stream({
    model: "claude-sonnet-4-5",
    max_tokens: 1024,
    tools: mcpToolsToAnthropicFormat(registry),
    messages: history
  });

  stream.on("text", (delta) => {
    res.write(`data: ${JSON.stringify({ delta })}\n\n`);
  });
  stream.on("end", () => res.end());
});

Why SSE and not WebSockets? Chat is almost entirely server→client; SSE gives you that over plain HTTP with built-in auto-reconnect, no upgrade handshake, and friendlier behavior through proxies and serverless platforms. First visible token dropped from ~4s to ~2.2s — a 45% cut — and perceived speed improved even more than the number suggests, because a moving cursor feels instant.

Lessons Worth Stealing

  • Tool descriptions are prompts. The single highest-leverage optimization was rewriting tool descriptions to say when to use the tool, not just what it does. Call accuracy jumped noticeably with zero code changes.
  • Fewer, broader tools beat many narrow ones. Fifteen overlapping tools confused the model; consolidating to seven with clear boundaries eliminated most wrong-tool calls.
  • Log every tool call with its arguments and latency. When the bot misbehaves, the tool-call log tells you in seconds whether the model chose badly, the schema let garbage through, or the backend was just slow.
  • Design for refusal. A tool that can say "no" cleanly (consent pending, rate-limited, not found) produces a chatbot that fails gracefully. Tools that throw produce a chatbot that lies.

Where This Goes

MCP is doing for AI integrations what REST did for web services: replacing a pile of bespoke glue with a contract both sides can rely on. The interesting engineering has moved up a level — not "how do I connect a model to my data," but "what should a model be allowed to do, and how does a user stay in control." That's a security and product question as much as a protocol one, and it's exactly where backend engineers earn their keep in the AI era.
